Antislop applied during the sweep, as requested. This is an audit, not a fix pass. No application source, design direction, or production event data was changed. New files are this report and its evidence folder.

Design Read: bilingual student cybersecurity club site for MUST undergraduates, in the existing dark editorial Geist Mono language. ENERGY 2 / RHYTHM 2 / MOTION 1, from `DESIGN.md`.

### 1. Error-state retry does not recover

Locations: `src/app/events/error.tsx:6-14`; the same handler exists in `src/app/admin/error.tsx:6-14`.

Reproduction on `/events`, in both languages:

1. Put malformed JSON into the isolated event store and open the route.
2. Confirm the localized error page renders.
3. Restore the valid eight-event store.
4. Click the retry button.
5. The error remains, zero event cards render, and no request is issued by the retry click. A full page reload immediately renders all eight cards.

Both components bind the button to `reset()`. The installed Next.js 16.3 documentation, `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md`, distinguishes `reset()` (re-render without fetching) from `retry()` (re-fetch and re-render). The latter matches these server-data errors.

Recommended fix: use the documented `retry` prop in both boundaries and add a regression test that restores the store before clicking. The recovery failure was reproduced on events; the matching admin boundary is confirmed by source inspection, not a separate forced admin page error.

Evidence: `events-en-retry.png`, `events-mn-retry.png`, and the retry/reload entries in `states.json`.

### 2. Hero fact contrast fails outside the scrim's strong region

Locations: `src/app/globals.css:321-334` (`.hero-content::before`) and `.hero-facts dt`; `src/app/matrix-field.tsx` draws the background dots.

The scrim exists, unlike the earlier audit's missing-scrim finding. Its radial fade still exposes the lower and outer fact labels to dots:

- At 312x667, Mongolian, a dot beneath the MUST-CTF participant label sampled `#4e4e4e`. The label is `#8c8c8c`, producing **2.47:1**, below 4.5:1.
- At 740x360, a dot under the founding label sampled `#383838`, producing **3.49:1**.
- At 1366x900, the sampled fact-label pixels cleared 4.5:1 in the inspected frame.

These failures occur with reduced motion too; pausing the animation does not solve them. Dot placement is randomized, so exact pixel positions vary between visits. The saved foreground/background pair holds one measured frame constant.

Recommended fix: protect the complete facts area with a sufficiently opaque backing or a separate scrim. Keep the shield motif; do not rely on random dot placement to preserve readability.

Evidence: `hero-312-foreground.png`, `hero-312-background.png`, `hero-740-foreground.png`; fact bounds in `details.json`. The narrow-frame failing pixel is at x=224, y=620.

### 3. Year-filter counts are too dim

Location: `src/app/globals.css:1782-1787` (`.year-count`).

Inactive counts use `#8c8c8c` with `opacity: 0.8`. On `#0a0a0a`, that composites to `#727272`, with **4.12:1** contrast. At 9.5px these are normal-size text and need 4.5:1. Active/hover counts use a brighter color at full opacity and pass.

Recommended fix: remove the extra opacity or choose a brighter count token. Check the inactive state, not only the selected filter.

Evidence: the `.year-count` failures in `contrast.json`; the skill contrast checker confirmed 4.12:1.

### 4. Admin touch targets are inconsistent

Locations: `src/app/globals.css:1976-1977`, `2035-2037`, `2110-2114`, and the phone-only input override at `2451-2454`.

Measured examples:

| Control | Viewport | Actual target | Project minimum |
|---|---|---|---|
| Delete event | 390px and 768px wide | 38px wide | 44px |
| New event control in selected-event editor heading | 312px, 390px, 768px wide | 63x36px | 44px high |
| Password, title, date and select fields | 768px wide | 40px high | 44px high |
| Featured checkbox label | 768px wide | 650x40px | 44px high |

The phone input override stops at 640px, so tablet/touch layouts retain 40px controls. The delete button only gains a minimum height on phones; its width remains 38px everywhere. These are violations of this project's stricter 44px rule, not a claim that every one fails WCAG 2.2's 24px AA target criterion.

Recommended fix: apply target minimums across touch-relevant widths, including the delete column, text controls, and checkbox label.

Evidence: admin entries in `measurements.json`; `admin-en-1366x900-editor.png`. The small checkbox input alone is not a separate finding because clicking its enclosing label also toggles it.

### 5. Tablet gallery loses its lead-photo hierarchy

Locations: `src/app/globals.css:697-700` and `1188-1189`.

`.gallery-cell-lead` initially sets a full-width basis. The later 940px media query sets `flex-basis: 340px` on every `.gallery-cell`, including the lead. At 768px, on the full gallery:

- Grid width: **704px**.
- Lead tile width: **344px**, the same as an ordinary tile.
- Lead image height: **192.4px**, versus **256.5px** for its neighboring 4:3 image.
- Both tiles stretch to a 300px row, leaving about **61px of unused space** below the lead's caption.

The same selector affects the About-page gallery band. The featured photograph loses its intended first read, and its different aspect ratio produces a conspicuous blank area.

Recommended fix: exclude the lead from the tablet basis override or explicitly preserve its 100% basis inside that breakpoint. Keep the ordinary tiles in two columns.

Evidence: `gallery-en-768-first-row.png` and `gallery-768-en` in `details.json`.

### 6. Native date-picker affordances do not match the dark surface

Location: `.form-field input` in `src/app/globals.css:2110-2124`; no dark `color-scheme` is declared.

In production Chromium, the date inputs have a near-black fill but retain black calendar icons. Black on `#0a0a0a` is **1.06:1**, below the human skill's 3:1 non-text requirement. Clicking that almost invisible icon opens a white native calendar, despite the surrounding dark form. The picker works; discoverability and surface consistency are the problem.

Recommended fix: declare an appropriate dark color scheme for native form controls and verify the date indicator and picker in supported browsers. Keep the native picker rather than replacing it with a new calendar component.

Evidence: `admin-date-control.png`, `admin-date-picker.png`, and `date-native` in `details.json` (`colorScheme: normal`, indicator filter `none`).

### 7. Narrow programme rows waste scarce reading width

Locations: `src/app/globals.css:944-946` and `1342-1347`.

At 312px, the programme card is about 270px wide but its copy column is only **130px**. The number track, arrow track, gaps and padding consume the other half. Descriptions wrap into short fragments and CCS Workshop breaks across two heading lines.

The static MUST-CTF card has no arrow, yet the phone rule still overrides its two-column layout with `34px 1fr 38px`, reserving an empty arrow track. At 390px the copy column improves to 208px, so this is most obvious on narrow phones.

Recommended fix: give narrow cards a full-width copy row, or move the number and arrow into a compact top row. At minimum, retain the static card's two-column override at phone widths. This is a composition change inside the existing design, not a reason to change the typeface.

Evidence: `about-en-312x780-programs.png` and the programme measures in `details.json`.

### 8. About-page density no longer matches the reference target

Locations: `.page-hero`, `.about-section`, `.gallery-section`, `.programs-section`, and `.join-inner` in `src/app/globals.css`; compact-page target in `DESIGN.md`.

At 1366px, `/about` is **4775px tall in English** and **4863px in Mongolian**. The direction names roughly 2900px for a content page. The page retains real content and varied sections, so this is not a template-content or overflow defect. It is a lower-priority direction deviation: large section padding and the full-shell-width lead photograph extend the page well beyond the compact reference.

Recommended next step: review the desktop vertical budget. Reduce repeated section padding and consider a capped lead-image height without dropping the photographs or changing the site's visual language. Treat 2900px as a reference, not a rigid requirement to squeeze both languages into identical heights.

Evidence: `about-en-1366x900.png` and About-page `scrollHeight` values in `measurements.json`.

## Delivery gate result for the audited UI

This report does not certify the UI as ready to ship, and no fixes were silently applied.

- Hard Gate: **FAIL**. Recovery, text contrast, and touch-target failures in findings 1-4. The non-text contrast supplement also fails in finding 6.
- Purpose-Gate: **PASS for the inspected visual techniques**. `DESIGN.md` records why Geist Mono, the shield-derived dots, dark palette, real photographs, and the restrained accent are used. Header/viewer blur separates foreground layers; menu shadow marks an overlay. No new assets or unexplained visual treatment introduced.
- Liveliness: **FAIL at the tablet gallery composition**, finding 5. Elsewhere the hierarchy, varied About sections, and brand motif remain recognizable. The documented shimmer/wash exception to MOTION 1 is preserved, not re-raised as an unapproved redesign request.
- Craftsmanship and Quality Locks: **FAIL**. Recovery is incomplete; narrow programme composition and desktop density need attention. Passing build/tests do not cover those visual failures.

Verification commands all passed: `npm run lint`, `npm run typecheck`, `npm test` (16 checks), and `npm run test:e2e` (production build plus 36 browser tests).

Limits: Chromium only; no physical-device keyboard, Safari/Firefox native-control check, actual browser 200% zoom, or complete screen-reader audit. The 683x450 check is a viewport/reflow check, not a claim of native 200% zoom testing. Gallery empty/loading branches were inspected in source; image-failure behavior was exercised in the browser. No Lighthouse score was used as a substitute for visual or contrast measurements.

Recommended fix order: 1-4, then 5-6. Choose whether to include the composition/density work in 7-8. Application changes require a separate approval.
